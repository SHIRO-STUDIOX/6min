# ADR-014 — Local SQLite, PostgreSQL Production and ordered PowerShell startup

Owner explicitly selected SQLite for local development with PostgreSQL for Production after being informed this requires dual-database support. This supersedes the PostgreSQL-only local setup recommendation, not the scoring/auth/import/commerce contracts or release gates. No existing PostgreSQL data is converted or deleted.

Use built-in node:sqlite (Node24+) without a new dependency, local service, Docker, downloaded database binary or trust bypass. start.ps1 (PowerShell5.1-compatible syntax) checks prerequisites and port, uses lock-hash-gated npm ci, applies schema/seed and launches Next in the foreground. Child failure stops the chain; existing servers are not killed. Ctrl+C stops Next and leaves durable SQLite data. Dedicated ignored .env.sqlite.local / .local-data files preserve .env/.env.local/PostgreSQL settings. Development/test files must differ, including case aliases on Windows and existing hard links; symbolic-link/junction paths are rejected. Files/folders get owner-only POSIX modes; Windows uses its normal filesystem ACLs, not an asserted POSIX ACL guarantee.

The Production adapter keeps native pg+Drizzle query/transaction behavior. Local adapter compiles the same bound Drizzle SQL and explicitly translates the small current SQL subset (JSON casts, time/interval functions, numeric/count projections). This is not a general PostgreSQL parser. Unsupported syntax fails rather than silently faking a result. Data values remain bound. JSON values/Booleans/dates/rational TEXT preserve application result contracts. Draft JSON comparison is structural. Canonical UTC microsecond timestamps maintain ordered attempts/corrections; Tehran calendar projection matches PostgreSQL.

SQLite transactions use BEGIN IMMEDIATE and a shared per-process async queue (also under local Next production preview), WAL, full synchronization and busy timeout. Thus removing row/advisory lock clauses is valid only inside a serialized real transaction. Cross-process writes are serialized by SQLite. Failed transactions stay aborted until rollback, even if a handler catches a constraint error; close/release rolls back. History/content triggers, FKs/checks/unique grants mirrored in an independent checksum-locked SQLite schema snapshot (PostgreSQL0001–0013), with future schema changes requiring explicit parity migrations/tests. Arbitrary-precision rational numerators/denominators stay TEXT and are computed in existing BigInt domain functions, not SQLite floating point. No tests substitute a client-computed score.

SQLite requires explicit SHISH_ENV=development/test and local path; Production requires PostgreSQL. Next NODE_ENV=production can mean local build/preview and is not itself a deployment realm. The local profile preloader validates SHISH_ENV and recognized setup keys, then exports them without changing the parent PowerShell environment. Use --import, not --env-file for Next CLI: Next forwards exec arguments into worker NODE_OPTIONS where --env-file is forbidden. Existing SMS/payment mocks remain failclosed outside development/test.

Single-writer SQLite is a local development choice, not a replacement Production capacity claim. PostgreSQL remains mandatory for actual deployment. Local backup and data transfer are separate concerns; never copy an active SQLite main file alone or silently import another database. Original Postgres/Docker helper remains optional/backward compatible. No UI/FSM/token redesign.

Validation: same integration and browser suites on both drivers, focused transaction/precision/path/production guards, actual PowerShell syntax/setup/start/HTTP/stop checks on Linux PowerShell. A Windows CI job is provided; local Linux evidence does not certify execution on the user's Windows machine or remote CI success. See the introducing change report for exact final results.
